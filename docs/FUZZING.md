# Fuzzing svccat

svccat parses YAML manifests, policy files, URLs and glob patterns that come out
of somebody else's repository — untrusted input, by definition. This document is
the working guide to the cargo-fuzz setup that hammers those parsers, and to the
committed regression corpus that keeps every input a past run found interesting
under test on every pull request.

**Three files are the source of truth; this document is pinned to all of them by
tests in `tests/fuzz_corpus_replay.rs`, so prose that drifts fails the PR gate
instead of quietly misleading the next reader:**

| Source of truth | What it settles | Guard test |
| --- | --- | --- |
| `fuzz/Cargo.toml` + `fuzz/fuzz_targets/` | which targets exist | `fuzz_targets_agree_across_sources`, `docs_describe_every_fuzz_target` |
| `.github/workflows/fuzzing.yml` | how CI runs them | `fuzzing_workflow_runs_from_the_committed_seed_corpus`, `docs_quote_the_workflows_actual_fuzz_command` |
| `fuzz/corpus_seeds/` | the committed regression inputs | `every_target_has_a_nonempty_seed_corpus`, the `*_seeds_replay_without_aborting` tests |

Every `fuzz/...` path named below is likewise checked to exist (or to be a
generated path listed in `fuzz/.gitignore`) by `docs_only_reference_fuzz_paths_that_exist`.

## Overview

Fuzzing feeds randomly generated bytes to svccat's parsers and validators to:

- find parsing bugs and unhandled panics
- find crashes that are *not* panics and therefore cannot be caught — the
  unguarded recursive `base` chain in the policy rule compiler aborted the
  process with a stack overflow (fixed in PR #16)
- discover resource-exhaustion paths
- reach edge cases unit tests do not think to write down

## Fuzz Targets

### 1. Manifest YAML parsing + inline policy rule compilation

**File:** `fuzz/fuzz_targets/fuzz_manifest.rs`

Parses arbitrary bytes as a `Manifest` (the same `serde_yaml`/`Deserialize`
path `Manifest::load` uses), and — when parsing succeeds — feeds the parsed
`policy.rules` straight into `RuleEngine::compile`, exactly as `svccat
check`/`workspace check` do via `src/drift.rs`. That second step is deliberate,
not incidental: fuzzing the parse-then-compile pipeline as one unit is what let
this target find the `base`-chain stack overflow automatically, rather than only
exercising YAML shape.

### 2. URL validation

**File:** `fuzz/fuzz_targets/fuzz_url.rs`

Feeds arbitrary strings into `svccat::urlvalidation::validate_url` (both the
`allow_localhost=false` and `=true` modes), the trust-boundary check used before
`--ping`/webhook requests go out (see `src/safe_http.rs` for the
redirect-hardening layered on top of it).

### 3. Glob pattern processing

**File:** `fuzz/fuzz_targets/fuzz_glob.rs`

Feeds arbitrary strings into `glob::Pattern::new`, the same pattern-compile call
`src/discovery.rs` makes for every `discovery.ignore` / `--ignore` pattern read
from a manifest or CLI flag.

### 4. File-based policy config parsing + evaluation

**File:** `fuzz/fuzz_targets/fuzz_policy.rs`

Parses arbitrary bytes as the **file-based** policy config
(`.svccat/policy.yaml`, `src/policy.rs`) and — when parsing succeeds — runs
`policy::check` against a fixed catalog, so arbitrary field names flow through
`has_field`'s match and arbitrary strings flow through the violation `format!`s.
This is a *different* type from the **inline** `manifest.policy` config target 1
exercises: the two share the name `PolicyConfig` and nothing else.

The fuzzed entry point is the deserialization + evaluation pipeline
`PolicyConfig::load` delegates to, not `load` itself: `load` takes a `&Path` and
does its own file I/O, so fuzzing it directly would fuzz the filesystem rather
than the parser. Everything `load` can reach on untrusted bytes is reached here.

## Running fuzzing locally

### Prerequisites

libFuzzer instrumentation needs a nightly toolchain **and** a working C/C++
toolchain (clang) to link the sanitizer runtime:

```bash
rustup toolchain install nightly
cargo install cargo-fuzz --locked
```

Nothing else needs initializing: `fuzz/Cargo.toml` is a standalone,
workspace-detached crate that depends on svccat via `path = ".."`, so a fuzz run
always exercises the checkout you are sitting on, never a published release.

If `cargo fuzz build` fails to link, you are missing clang, not a Rust
component. That is the normal state of a stock Windows dev box, and it does not
block verifying a change to the fuzzing setup — see
[Verifying a fuzzing change without a local toolchain](#verifying-a-fuzzing-change-without-a-local-toolchain).

### Run one target

```bash
# 10 minutes on the manifest parser, starting from the committed seeds
cargo fuzz run fuzz_manifest fuzz/corpus/fuzz_manifest fuzz/corpus_seeds/fuzz_manifest \
  -- -max_total_time=600
```

The corpus arguments are the same ones CI passes, in the same order, and the
order is load-bearing — see [CI Integration](#ci-integration).

### Run every target

```bash
for target in fuzz_manifest fuzz_url fuzz_glob fuzz_policy; do
    echo "Fuzzing $target..."
    mkdir -p "fuzz/corpus/$target"
    cargo fuzz run "$target" "fuzz/corpus/$target" "fuzz/corpus_seeds/$target" \
      -- -max_total_time=300
done
```

### Reproduce a single input

Corpus directories and individual input files are positional arguments to
`cargo fuzz run`, **before** the `--` separator
(`cargo fuzz run [OPTIONS] <TARGET> [CORPUS]... [-- <ARGS>...]`); everything
after `--` is handed to libFuzzer as a flag:

```bash
cargo fuzz run fuzz_manifest fuzz/artifacts/fuzz_manifest/crash-3d41d6e74dcf6
```

### Coverage

```bash
cargo fuzz coverage fuzz_manifest fuzz/corpus/fuzz_manifest fuzz/corpus_seeds/fuzz_manifest
```

This writes LLVM profile data under `fuzz/coverage/` (already excluded by
`fuzz/.gitignore`). Rendering it as HTML is a separate llvm-cov step
(`cargo cov -- show ...`): `cargo fuzz coverage` has no report-format flag of
its own, and arguments after `--` go to libFuzzer, not to a report generator.

## When a fuzz run finds a crash

This is the workflow that keeps a found bug found. Steps 4 and 5 are the ones
that are easy to skip and the reason the committed corpus exists at all.

1. **Get the crashing input.** Locally, libFuzzer writes it to
   `fuzz/artifacts/<target>/crash-<hash>` and prints the path. In CI the job
   fails and its `Upload crash artifacts` step publishes the file as the
   `fuzz-crash-<target>` artifact on the workflow run page — download it from
   there.
2. **Reproduce it** with `cargo fuzz run <target> <path-to-input>` (see above).
   Note that a crash here is often *not* a panic: an abort or stack overflow is
   not catchable, which is why these are worth reproducing directly rather than
   wrapping in `catch_unwind`.
3. **Fix the code** so the input produces a normal `Err` (or a correct value),
   never an abort.
4. **Commit the input as a seed:**

   ```bash
   cp fuzz/artifacts/<target>/crash-<hash> fuzz/corpus_seeds/<target>/<descriptive_name>
   ```

   Name it for the defect (`base_cycle_self`, `required_not_a_list`), not for
   its hash. Keep it small; `cargo fuzz tmin <target> <input>` minimizes it
   first if it is not.
5. **Pin the contract in the replay suite.** Simply committing the file already
   gets it replayed on every PR — `tests/fuzz_corpus_replay.rs` walks every file
   in `fuzz/corpus_seeds/<target>/` and drives it through the same call the fuzz
   target makes. But "did not abort" is a weak contract. If the fix has a
   specific one (a cycle must yield `Err`, a malformed policy must fail to parse
   rather than silently produce an empty config), assert it by name, next to the
   existing assertions of the same shape.

## The committed regression corpus

`fuzz/corpus_seeds/<target>/` is a normal, committed part of the test suite, not
fuzzer scratch space. It exists because the Continuous Fuzzing workflow does not
run on `pull_request` (see below), so without it nothing at PR time would prove
that inputs a past campaign found interesting are still handled.

Two properties are worth knowing before adding to it:

- **Each `drive_*` helper in `tests/fuzz_corpus_replay.rs` is a byte-for-byte
  mirror of the body of the fuzz target with the same name.** Change a target,
  change its mirror in the same commit, or the replay stops testing what CI
  fuzzes.
- **Each corpus contains one 0-byte `empty` seed.** libFuzzer folds it into its
  own synthetic empty unit, so a run's `seed corpus: files: N` line reads one
  below the committed file count. That is expected and does not mean a seed was
  rejected.

The corpora are also fed to the fuzzer itself as read-only seed input, so the
daily campaign starts from them instead of from nothing.

## CI Integration

`.github/workflows/fuzzing.yml` ("Continuous Fuzzing") runs this for real, on
`push` to `main`, once a day (`0 0 * * *`), and on manual
`workflow_dispatch`. It does **not** run on `pull_request` — fuzzing is a
push/schedule/manual concern, not a per-PR gate, so it never adds time to a
merge. It matrices the four real targets above, one job per target, each
running

```bash
cargo fuzz run <target> fuzz/corpus/<target> fuzz/corpus_seeds/<target> \
  -- -max_total_time=120
```

against a nightly toolchain, and uploads the crashing input as a build
artifact on failure so it can be downloaded and reproduced locally.

Two details of that command matter:

- **120 seconds** is a deliberately CI-sane libFuzzer budget — enough to catch
  cheap, shallow crashes like the unguarded recursive `base` chain above on
  every push and once a day, without turning this into a multi-hour runner.
- **The corpus arguments are ordered.** libFuzzer writes newly discovered
  inputs into the *first* corpus directory and treats every later one as
  read-only seed input, so the gitignored working corpus
  `fuzz/corpus/<target>` comes first and the committed
  `fuzz/corpus_seeds/<target>` comes second. A CI run therefore starts from
  the committed seeds without ever mutating them.

Read the actual workflow file for the current exact steps; it is the source of
truth, not this paragraph.

### Verifying a fuzzing change without a local toolchain

Because the workflow declares `workflow_dispatch`, the whole matrix can be run
**from a branch, before merging**, which is how a change to the targets, the
corpora or the run step gets verified on a machine that cannot build libFuzzer
locally:

```bash
gh workflow run fuzzing.yml --ref autodev/my-branch
gh run list --workflow fuzzing.yml --branch autodev/my-branch --limit 1
```

The run logs carry the numbers worth quoting in a PR body: each leg's
`INITED cov: ... corp: N/Mb` line shows how much of the corpus was actually
loaded, so a seeding or wiring change has a measurable before and after.

## Best Practices

1. **Keep sessions long.** The 120-second CI budget catches shallow crashes; a
   real bug hunt wants minutes to hours on one target.
2. **Commit interesting inputs.** Anything that crashed, or that reached a new
   branch worth protecting, belongs in `fuzz/corpus_seeds/<target>/` — see
   [When a fuzz run finds a crash](#when-a-fuzz-run-finds-a-crash). Nothing
   reads any other directory: seeds committed elsewhere are dead files.
3. **Minimize before committing.** `cargo fuzz tmin <target> <input>` shrinks a
   crash to the smallest input that still reproduces it, which makes the seed
   readable as documentation of the bug.
4. **Every crash gets a named assertion**, not just a committed file. "Did not
   abort" is the floor, not the contract.
5. **Watch memory.** Unbounded `Vec`/`HashMap`/`String` growth on untrusted
   input is a finding even when nothing crashes; `src/manifest.rs`'s
   `MAX_MANIFEST_SIZE`/`MAX_SERVICES` limits exist for exactly this reason.
6. **Keep `libfuzzer-sys` current** for better instrumentation.

## Troubleshooting

### `cargo fuzz build` fails to link, or reports a missing LLVM/clang

libFuzzer needs a C/C++ toolchain. Install one:

```bash
# macOS
brew install llvm

# Ubuntu
sudo apt-get install clang llvm

# Windows: install LLVM from https://releases.llvm.org/ and put clang on PATH
```

A dev box without clang cannot run cargo-fuzz at all. That is a normal state,
not a broken checkout — use the branch dispatch described above to verify
fuzzing changes, and rely on `cargo test` for the PR-time guards, which need no
fuzzing toolchain.

### Fuzzer reports "timeout"

Raise the per-input timeout, or fix the slow path it found:

```bash
cargo fuzz run fuzz_manifest -- -timeout=10  # 10 seconds per input
```

### Out of memory during fuzzing

```bash
cargo fuzz run fuzz_manifest -- -rss_limit_mb=512
```
